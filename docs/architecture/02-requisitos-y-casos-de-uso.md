# 02. Especificación funcional, casos de uso e historias

## 1. Alcance y prioridades

La decisión funcional de partida es un servicio web responsive, asistido por facilitadores, y no un terapeuta digital. Las prioridades siguientes son **recomendaciones para MVP**; no todas son compromisos aprobados del cliente. MUST no significa autorización ética/legal: indica dependencia funcional para el MVP propuesto. Los elementos marcados Won't se excluyen del MVP salvo nueva aprobación.

### Funcionalidades inventariadas

| Estado | Capacidades |
|---|---|
| **Existente** | Chat anónimo de FAQ RAG, respuesta extractiva local, generación opcional Groq, fuentes/citas, abstención, señal heurística por palabras, respuestas en español, historial visual efímero no enviado al servidor, health check. Véase [auditoría](01-auditoria.md). |
| **Ausente** | Cuentas, login/recuperación, roles, consentimientos, onboarding, base de participantes/actividades, biblioteca navegable, check-ins, progreso, recordatorios, paneles, exportación, atención humana integrada, preferencias, derechos de titulares, aprobación editorial y auditoría. |
| **Defectuoso/riesgoso para el objetivo** | Error de red indistinguible de ausencia de evidencia en UI; seguimiento conversacional no conserva el tema y puede abstenerse; regex no semántica usada para señal de riesgo; el prompt estructurado no elimina prompt injection; sin control de acceso/rate limit; falta de persistencia operativa/backups. No implica que todas estas condiciones sean vulnerabilidades explotadas. |
| **Futuro** | WhatsApp/SMS sujeto a viabilidad/consentimiento, foro moderado, perfil descriptivo del profesional, simulador, role-play y avatar. Requieren validación separada. |

## 2. Requisitos funcionales priorizados

Criterio común de aceptación: cada requisito debe tener cobertura automatizada (unidad/integración o permiso) y evidencia registrada para el DoD; pruebas de interfaz se añaden donde se indica. Los endpoints son nombres de propuesta, no implementados hoy.

| ID | Prioridad | Propósito; actor | Reglas y dependencias | Criterio de aceptación verificable |
|---|---|---|---|---|
| RF-01 Identidad | Must | Crear y acceder a cuenta; cuidador | Email verificado o mecanismo aprobado; contraseña almacenada con hash adaptativo; throttling; recuperación de un solo uso, sin revelar existencia de cuenta. Dep.: seguridad, aviso privacidad. | Registro/login/logout/recuperación cubiertos; credenciales válidas acceden, inválidas y expiradas no; mensaje de recuperación no revela si el email existe. |
| RF-02 Roles | Must | Controlar acceso por rol y relación; todo personal | Roles separados, deny-by-default, autorización en backend, alcance de participante asignado/estudio. Dep.: RF-01, matriz de [04](04-datos-privacidad-ia-seguridad.md). | Tests positivos y negativos para cada ruta y acceso cruzado a participante; 403/404 consistente sin fuga de existencia. |
| RF-03 Consentimientos | Must | Registrar consentimiento; participante/estudio | Servicio separado de investigación, versiones fechadas, finalidades, retirada, evidencia mínima y estados; no inferir aceptación por uso. Dep.: protocolo/aprobaciones. | No se habilitan funciones del estudio hasta consentimiento vigente; registrar versión/hora/canal; revocación bloquea tratamientos dependientes y crea tarea de revisión de retención. |
| RF-04 Onboarding | Must | Recolección mínima; cuidador | Preguntas cerradas aprobadas, opcionales donde sea posible, evitar nombre/fecha exacta/detalles identificables del niño; permitir corregir. Dep.: RF-03, estudio/cohorte. | Usuario completa/revisa; validaciones visibles; solo campos aprobados se guardan y la respuesta individual no aparece en panel técnico agregado. |
| RF-05 Programa y cohortes | Must | Asociar participante a programa; coordinador | Cohorte, sesión y calendario versionados; no permitir asignación no autorizada. Dep.: RF-02, configuración del estudio. | Participante solo ve sesiones habilitadas para su cohorte; acceso a cohorte ajena denegado y auditado. |
| RF-06 Biblioteca | Must | Encontrar contenido aprobado; cuidador | Contenidos publicados, filtros por tema/sesión/formato/edad de programa definidos; búsqueda solo sobre catálogo visible. Dep.: RF-05, RF-17. | Los filtros retornan únicamente contenidos publicados vigentes; vacío y error tienen estados accesibles. |
| RF-07 Prácticas | Must | Guiar práctica breve; cuidador | Tarjetas/guiones ligados a sesión, duración y objetivo descriptivo; validación editorial; no personalizar clínicamente. Dep.: RF-17. | Tarjeta aprobada se muestra con fuente/versión y acción de marcar completada; borrador/rechazada nunca aparece en participante. |
| RF-08 FAQ RAG | Must | Consultar preguntas sobre documentos oficiales; cuidador | Corpus cerrado aprobado, citas con documento/versión/ubicación; umbral validado; abstener si baja evidencia; sin generación libre OOD. Dep.: RF-17, evaluación RF-19, políticas de proveedor. | En suite dorada, cada respuesta tiene citas válidas; casos sin evidencia abstienen; no citar fuente retirada; proveedor deshabilitado por defecto hasta aprobación. |
| RF-09 Guía inmediata | Must | Ofrecer pasos preaprobados; cuidador | Flujos deterministas con ramas revisadas, alternativas de seguridad; sin generación como respuesta principal. Dep.: profesionales, teléfonos/horarios y RF-10. | Cada rama termina en mensaje revisado o derivación; fixtures de todos los caminos; botón de salida/ayuda disponible. |
| RF-10 Riesgo/escalamiento | Must | Solicitar/revisar apoyo humano; participante, profesional | Señal no diagnóstica; consentimiento/aviso; datos mínimos; definir responsable, horario, tiempos y fuera de cobertura; urgencia separada de soporte regular. Dep.: protocolo humano y aprobación legal/ética. | Señal crea tarea segura solo para equipo asignado; participante recibe expectativas honestas y alternativas aprobadas; prueba de no asignación a otro profesional. |
| RF-11 Check-in | Must | Autorregistro breve de actividad/estado; cuidador | Instrumento y frecuencia aprobados; no diagnóstico; opción de omitir/corregir; separar de texto libre. Dep.: protocolo, RF-03/04/05. | Check-in guarda solo campos permitidos, estado/fecha/cohorte; reenvío idempotente; no obliga narrativas. |
| RF-12 Progreso | Should | Mostrar acciones completadas; cuidador | Presentar avance descriptivo, no evaluación clínica ni ranking; definir ventana y fuentes de conteo. Dep.: RF-11, RF-07. | El total visible coincide con eventos aceptados del usuario en ventana; usuario no ve datos ajenos. |
| RF-13 Solicitud de apoyo | Must | Pedir contacto profesional; participante | Categoría/horario/canal mínimo; no prometer respuesta inmediata; confirmar recepción/alternativas. Dep.: RF-10, contacto aprobado. | Solicitud queda con estado y responsable; duplicados se controlan; interfaz muestra plazo vigente configurado o que no está disponible. |
| RF-14 Panel agregado | Must | Ver operación agregada; administrador técnico/coordinador autorizado | Sin respuestas individuales de caracterización; umbrales de supresión de celdas pequeños; agregados por cohorte/periodo únicamente. Dep.: eventos minimizados, RBAC. | Revisión de payload y pruebas verifican ausencia de identificadores/respuestas individuales; filtros limitan celdas con tamaño <k aprobado. |
| RF-15 Vista profesional | Should | Acompañar asignados; psicólogo/facilitador | Solo asignados, solo campos necesarios y autorizados; resumen estructurado descriptivo, no inferencia IA/diagnóstico. Dep.: asignación, consentimiento/ética, autorización. | Acceso cruzado denegado; datos visibles enumerados por campo; cada acceso queda auditado y puede revisarse. |
| RF-16 Exportación de investigación | Should | Extraer datos codificados aprobados; investigador/coordinador | Solicitud autorizada, alcance limitado, ID seudónimo, registro de export, agregación si posible; identidad separada. Dep.: protocolo, acuerdos, RF-02. | Export cumple esquema aprobado; no incluye contacto/identificadores; queda usuario, propósito, filtros, fecha y checksum en auditoría. |
| RF-17 Versionado editorial | Must | Crear/revisar/publicar contenido/prompts/flujo; editor y validador | Separación autor/revisor/publicador; versión inmutable, fuente/licencia, vigencia, cambios y rollback. Dep.: actores definidos. | No se publica sin aprobador; respuesta/contenido cita versión; retiro evita nuevas consultas y conserva auditoría. |
| RF-18 Preferencias y recordatorios | Should | Configurar recordatorios; cuidador/coordinador | Opt-in por canal/frecuencia y zona horaria; quiet hours; cancelar fácilmente; email inicial, SMS/WhatsApp sujetos a evaluación. Dep.: proveedor aprobado, RF-03. | No se envía sin preferencia vigente; revocación suprime colas pendientes; entrega/rebote se registra sin cuerpo sensible. |
| RF-19 Métricas de calidad/uso | Must | Medir uso, adherencia y RAG; investigador/coordinador | Definiciones reproducibles, cohortes/periodos, supresión, variables del protocolo claramente separadas. Dep.: eventos, aprobaciones. | Fórmulas/denominadores documentados y reproducibles; valores faltantes distinguidos de cero; export queda versionado. |
| RF-20 Derechos y privacidad | Must | Atender consulta/corrección/revocación/supresión; titular y responsable | Verificar identidad proporcionalmente; derivar solicitudes; conservar evidencia mínima de gestión; no prometer borrado si obligación de retención aplica sin revisión. Dep.: asesoría jurídica, política. | Cada solicitud tiene ticket, responsable/plazo interno y resultado; corrección actualiza fuente; revocación y supresión se propagan a copias/terceros conforme política aprobada. |
| RF-21 Auditoría/backups | Must | Investigar acción operativa y recuperar; seguridad/operador | Logs de eventos sin contenido sensible por defecto; control de acceso; backup cifrado; restauración ensayada. Dep.: arquitectura de alojamiento, RF-02. | Prueba periódica de restauración cumple RPO/RTO aprobados; eventos críticos incluyen actor/acción/objeto/fecha sin contraseñas/prompt completo. |
| RF-22 Foro moderado | Won't MVP / Could | Comunicación entre participantes; moderador | No se habilita hasta plan de moderación, reporte, respuesta, horario, protección de menores, consentimiento y evaluación de daño. | Gate explícito de aprobación; si se aprueba, contenido reportable/moderable y SLA probado antes de producción. |
| RF-23 Simulador/role-play/avatares | Won't MVP / Could fase posterior | Practicar escenarios | Solo después de validar seguridad, presupuesto, resultados y protocolo; Role-play no se confunde con apoyo real. | No está accesible por bandera/endpoint en MVP; aprobación separada y evaluación previa si se desarrolla. |
| RF-24 WhatsApp/SMS | Won't MVP / Could evaluación | Recordatorios/enlaces y soporte limitado | Evaluar privacidad, costo, interoperabilidad, conservación y opt-in; no enviar narrativas sensibles. | Informe de factibilidad/terceros aprobado antes de integración; consentimiento granular y revocación comprobada. |

## 3. Casos de uso y excepciones

Actores y capacidades se definen en [04-datos-privacidad-ia-seguridad.md](04-datos-privacidad-ia-seguridad.md#2-actores-y-matriz-de-permisos). Excepciones comunes: servicio/DB/proveedor no disponible; sesión expirada; rol o vínculo insuficiente; consentimiento vencido/retirado; contenido retirado. No degradar a respuesta de IA insegura ante fallo.

| CU | Flujo (precondición → acción → resultado) | Excepciones/reglas |
|---|---|---|
| CU-01 Registrar participante | Invitación/enlace válido → crea cuenta, verifica contacto y acepta términos de servicio separados de investigación → cuenta activa, sin consentimiento de investigación presumido. | Invitación inválida/duplicado devuelve mensaje neutro; no guardar estudio si consentimiento ausente. |
| CU-02 Gestionar consentimiento | Usuario autenticado ve finalidad/versión → acepta o rechaza por separado servicio, investigación, sensibles, contacto profesional y canales opcionales → versión/fecha/alcance registrados. | Rechazo mantiene únicamente servicio no dependiente si está aprobado; retirada desactiva tratamiento vinculado y genera revisión. |
| CU-03 Completar onboarding | Consentimiento requerido vigente y cohorte asignada → responde preguntas cerradas mínimas, revisa → caracterización mínima guardada con seudónimo. | Abandono guarda borrador solo si aprobado; campos opcionales pueden quedar vacíos; no pedir identificadores del niño. |
| CU-04 Consultar contenido | Usuario autenticado → filtra por cohorte, sesión, tema y formato → abre contenido publicado y su versión. | Sin resultados, contenido expirado o servicio caído comunica estado; jamás exponer borrador. |
| CU-05 Preguntar FAQ | Usuario autenticado y elegible → pregunta → backend recupera solo corpus aprobado, aplica umbral, retorna citas/verión o abstención. | OOD/ambigüedad abstiene; proveedor caído cambia a extractivo aprobado o explica indisponibilidad; sin guardar chat por defecto. |
| CU-06 Ejecutar guía inmediata | Usuario selecciona situación → contesta opciones de rama → recibe guía profesional preaprobada y opción de apoyo. | Señal sensible detiene generación y muestra protocolo validado; sin operador disponible se comunica alternativa/horario, sin promesa de seguimiento. |
| CU-07 Completar check-in | Usuario elegible abre check-in vigente → responde campos estructurados/omite → evento de actividad se guarda y progreso se recalcula. | Idempotencia previene duplicados; puede corregir según política; no interpretación clínica automática. |
| CU-08 Solicitar apoyo humano | Usuario revisa consentimiento/canal → envía solicitud mínima → acuse, estado y expectativa real. | Fuera de horario: instrucción no urgente/urgente validada; errores permiten reintento sin duplicar. |
| CU-09 Atender señal de riesgo | Regla o solicitud crea señal → profesional autorizado la revisa según procedimiento → resuelve/escala y registra acción mínima. | Señal no equivale a diagnóstico; falso positivo/falso negativo documentados; sin cobertura se activa protocolo institucional, no bot improvisado. |
| CU-10 Recordatorio | Preferencia y horario vigentes → job selecciona acción y canal → entrega resultado de proveedor, sin contenido sensible. | Desuscripción, quiet hours, rebote, duplicado o proveedor caído; cola no envía tras revocación. |
| CU-11 Consultar métricas agregadas | Rol autorizado define cohorte y ventana → se aplica supresión de grupos pequeños → muestra conteos agregados. | No hay endpoint de filas individuales para administración técnica; filtros/combos que reidentifican se bloquean. |
| CU-12 Exportar investigación | Protocolo/alcance autorizado → investigador solicita variables/ventana → sistema genera dataset seudónimo y bitácora. | Sin autorización se deniega; nunca incluir tabla de identidad; export sensible requiere confirmación y expiración/borrado controlado. |
| CU-13 Publicar contenido | Editor crea borrador con fuente/licencia/versión → validador profesional lo revisa → publicador libera → visible desde fecha vigente. | Autor no aprueba su propio contenido; rollback conserva historial; contenido con duda no se publica. |

## 4. Historias de usuario Given/When/Then

Los IDs enlazan a requisitos; interfaces/servicios/endpoints propuestos están en [03-arquitectura-y-api.md](03-arquitectura-y-api.md#8-contratos-de-api-propuestos). Pruebas `T-*` están definidas en [05-roadmap-validacion.md](05-roadmap-validacion.md#6-pruebas-y-definition-of-done).

| ID/prio/traza | Given / When / Then verificable |
|---|---|
| HU-01 Must · RF-01/02 · Identity / `POST /api/v1/auth/register` · T-AUTH | **Given** invitación válida y email no registrado, **When** participante registra credencial, **Then** recibe verificación y no ve datos de estudio antes de completar pasos autorizados. |
| HU-02 Must · RF-03/20 · Consent / `GET,POST /api/v1/consents` · T-CONSENT | **Given** versión activa visible, **When** titular acepta solo el servicio, **Then** el sistema registra esa finalidad y no habilita investigación ni mensajes opcionales. |
| HU-03 Must · RF-04 · Participant / `PUT /api/v1/me/onboarding` · T-PRIV | **Given** onboarding autorizado, **When** cuidador responde selección múltiple, **Then** datos mínimos quedan asociados a ID de estudio y no se solicita nombre del niño. |
| HU-04 Must · RF-06/07/17 · Content / `GET /api/v1/content` · T-CONTENT | **Given** contenido aprobado para cohorte, **When** usuario filtra tema/sesión, **Then** solo ve versión vigente y una prueba de borrador resulta 404/403. |
| HU-05 Must · RF-08/19 · Assistant / `POST /api/v1/assistant/faq` · T-RAG | **Given** pregunta cubierta por fuente aprobada, **When** pregunta, **Then** respuesta incluye IDs de documentos y pasajes; con pregunta no cubierta, el sistema abstiene y ofrece alternativa sin generar afirmaciones. |
| HU-06 Must · RF-09/10/13 · Safety / `POST /api/v1/guides/{id}/steps` · T-SAFETY | **Given** flujo revisado, **When** selecciona opciones, **Then** recibe rama preaprobada; la petición de contacto muestra disponibilidad y no diagnostica. |
| HU-07 Must · RF-11/12 · Activity / `POST /api/v1/check-ins` · T-ACTIVITY | **Given** check-in vigente, **When** guarda dos veces la misma solicitud, **Then** solo hay un evento lógico y el progreso refleja el resultado acordado. |
| HU-08 Must · RF-10/15 · Professional / `GET /api/v1/professional/participants/{id}/summary` · T-RBAC | **Given** profesional asignado y permiso actual, **When** abre resumen estructurado, **Then** solo ve campos autorizados; al cambiar ID a no asignado se deniega. |
| HU-09 Must · RF-14/19 · Admin técnico / `GET /api/v1/admin/metrics` · T-AGG | **Given** administrador técnico, **When** solicita métricas, **Then** recibe agregados y no puede consultar respuestas individuales ni deshacer anonimización por filtros. |
| HU-10 Should · RF-16 · Researcher / `POST /api/v1/research/exports` · T-EXPORT | **Given** investigador autorizado y dataset aprobado, **When** solicita export, **Then** recibe variables seudónimas permitidas y bitácora de alcance; datos identificables quedan ausentes. |
| HU-11 Should · RF-18/24 · Participant / `PUT /api/v1/me/preferences` · T-NOTIFY | **Given** canales opcionales, **When** participante desactiva WhatsApp, **Then** se eliminan envíos en cola y no se contacta por ese canal. |
| HU-12 Must · RF-17 · Editor/validador / `POST /api/v1/editorial/items/{id}/publish` · T-CONTENT | **Given** editor y revisor distintos, **When** se aprueba contenido con fuente/licencia, **Then** nueva versión queda inmutable, visible y trazable; autoaprobación se deniega. |
